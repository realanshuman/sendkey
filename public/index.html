How it works

The key never touches the server

Not as a policy we promise to follow — as a property of how URLs work.

1

Sealed in your browser

Your browser generates a random 256-bit key and encrypts the secret locally. Only the ciphertext is uploaded — the key stays with you.

2

Key rides in the # fragment

The link's fragment is the one part of a URL browsers never put on the wire. It's absent from the request, the Referer header, and every access log.

3

Destroyed on first read

Opening the link atomically deletes the stored ciphertext. Fifty people can click at once — exactly one of them gets the secret.

Because the key bypasses the server entirely, a database breach yields a pile of AES-256-GCM blobs and nothing that can open them.

Security

Built so trust isn't required

Every guarantee below is a structural property, backed by tests in the repo.

End-to-end encrypted

AES-256-GCM via the Web Crypto API. Authenticated encryption, so a tampered ciphertext fails to open rather than decrypting to garbage.

Atomic burn

Read-and-delete happens as one indivisible operation. Under fifty simultaneous readers, exactly one wins — never two.

Expires no matter what

Every secret carries a hard TTL. Unread secrets are swept from storage automatically — nothing lingers because someone forgot to open it.

Optional passphrase

A second layer derived with PBKDF2-SHA256 at 310,000 iterations, nested inside the burn — so a typo can be retried offline, forever.

No accounts, no analytics

No sign-up, no cookies, no third-party scripts. A strict CSP blocks every external origin, so nothing can phone home.

Auditable and self-hostable

One Go binary, zero third-party dependencies, MIT licensed. Read the whole thing in an afternoon, then run it yourself.

FAQ

Straight answers

Can you really not read my secret?
Correct, and it isn't a matter of policy. Encryption happens in your browser and the key is placed after the # in the link. Browsers never transmit the fragment — it's not in the request line, not in the Referer header, not in any server log. We receive ciphertext and a nonce; without the key, that's noise.
What if someone intercepts the link?
Then they have the secret — the link is the secret. Send it through a channel you trust, keep the expiry short, and add a passphrase for anything sensitive. The upside of burn-after-reading is that you find out: if your recipient reports the link already dead, someone else opened it.
Why is the passphrase checked in my browser instead of on the server?
Because a server-side check would have to either destroy the secret on a typo, or hand attackers an oracle to guess against. Nesting the passphrase layer inside the encrypted envelope means the single fetch already happened, the ciphertext is on your machine, and you can retry as many times as you like without anyone knowing or anything burning.
What happens if nobody opens the link?
It expires on its own — one hour, one day, or seven days, your choice. Expired secrets are swept from storage whether or not they were ever read.
Can I use this for files?
Not yet. SendKey is tuned for credentials and short text — up to 128 KB per secret. Encrypted file transfer is a different set of trade-offs (chunking, resumability, storage cost) and isn't built in.
What are the limits of this design?
Two worth naming. First, anyone holding the link before your recipient can read the secret — the link is the credential. Second, browser-based encryption relies on the page you're served being honest; a malicious operator could ship tampered JavaScript. That's true of every encrypt-in-the-browser tool. If it matters, use the CLI, whose binary you built yourself, or self-host.
Can I self-host it?
Yes — that's the intended deployment for anything serious. It's one Go binary with no third-party dependencies: sendkey serve and you're running. It stores secrets in memory by default, or in Redis when KV_REST_API_URL is set. Deploys to Vercel unchanged.
